Sabha notifications architecture

One dispatcher decides what fires per recipient per event across all channels — in-app rows, push, missed-notification email bundles, and the weekly activity digest. Bundled email replaces V0's per-event delayed sends. Tenant-safe by construction; defaults safe.

01 Architectural goals

Six load-bearing principles. Everything else in this document is downstream of these.

01

One dispatcher

Decides what fires per recipient per event across all channels. No more split decision trees in Room::MessagePusher, Message callbacks, and "email nowhere."

02

Bundled missed-email

Hourly or daily bundles, user-selectable, instead of per-event delayed sends.

03

Separate digest pipeline

Different copy, different cadence, different opt-out, different gates. It is not a degenerate bundle.

04

Send-time revalidation

State changes during the bundle window — return, block, delete, opt-out — drop items at delivery time. Single cancellation path.

05

Tenant-safe by construction

Per-workspace settings, bundles, digest. Identity and email address are the only untenanted touchpoints.

06

Default safe

Email feature-flagged off at the workspace level. Both email surfaces default off for users.

02 Channels

Four output targets. Independent — a user can be a row recipient and not a push recipient; a bundle item and not a digest recipient.

●

In-app row

Per-message, when activity_type creates a Notification row.

notifications (existing)
↗

Push (WebPush)

Per-message, when membership is push-eligible and disconnected.

push_subscriptions (existing)
✉

Missed-notification email

Eligible items accumulate into a per-user bundle and deliver hourly or daily.

notification_bundles + notification_bundle_items (new)
∎

Weekly activity digest

Recurring per-workspace job, generated content for opted-in members.

last_digest_sent_at (per user)

04 Routing dispatcher

One job per message, not one job per (message, activity_type). Substance lives on the model — the job is a shallow wrapper.

Trigger Message create / thread reply
Job Notification::DispatchJob.perform_later(message)
Model Message#notify_recipients
Iterate For each activity_type in Room#applicable_activity_types(message)
In-app deliver_in_app_row_for(activity_type)
Push deliver_push_for(activity_type)
Bundle enqueue_missed_email_candidates_for(activity_type)

In-app row creation is a pass-through for :mention and :thread_reply. The legacy create_mention_notifications and create_thread_reply_notifications callbacks still own row creation; deliver_in_app_row_for only writes a row for :boost. The partial unique index index_notifications_on_message_user_type is the safety net if both paths ever fire.

Boost is the lone exception. Triggered after a Boost create, not a Message. Uses Notification::DispatchJob.perform_later(message, only: :boost, actor: booster). Only call site that uses only:.

After-commit ordering matters

Message already has eight after_create_commit callbacks. The new dispatch callback must fire after create_mention_notifications and update_thread_reply_count, because the dispatcher reads mention notifications and thread-count state.

05 Eligibility — Membership::Notifiable

A single concern on Membership answers per-channel eligibility. The same predicates run at dispatch time and delivery time, so state changes flow through one gate.

Common gates all channels

  • Recipient is not the message creator (except for :direct_message accounting)
  • Recipient is active, verified, not banned, not deactivated, not a bot
  • Recipient and sender are not blocked in either direction
  • Message and room are active
  • Membership is active and effective_involvement authorizes this activity_type

Push disconnected

  • user.push_enabled?
  • Membership not currently connected? (60-second WebSocket TTL, room-scoped)

Missed-notification email workspace-locally away

  • user.missed_email_enabled?
  • Account email flag on
  • user.workspace_locally_away? — last connection > 1 hour ago in this workspace
  • activity_type.in?(EMAIL_TYPES)

Weekly digest no message arg

  • user.weekly_digest_subscribed?
  • Account weekly_digest_enabled?

Two distinct presence checks

Push uses per-membership connected? (room-scoped, 60-second TTL). Email uses workspace_locally_away? (queries Membership.last_connected_at_for([id]) against the :away activity tier — 1 hour — workspace-local, not cross-workspace). The 1-hour tier is chosen over the tighter 10-minute :active tier because email asks "has the user been gone long enough that an email is the right way to reach them?", not "should we show a green dot?"

effective_involvement folds the two-source rule

Predicates ask effective_involvement only — they don't read mode and involvement independently. Rule:

1
Per-room involvement == "everything"

Effective is "everything" — per-room opt-in beats global mute.

2
Else if global mode == "nothing"

Effective is "nothing" — global mute applies.

3
Else use per-room involvement

(mentions / nothing / invisible)

Snooze / DND is not a v1 feature, in any form. No snooze_until column, no snooze_indefinite flag, no presence-as-snooze fallback beyond workspace_locally_away?. All "user is unavailable" suppression rides on passive presence and the per-channel master switches.

07 Missed-notification email pipeline

Eligible event lands in the active bundle. Bundle's ends_at fires BundleDeliveryJob. Each item is re-evaluated at delivery; survivors get a single email.

1
Eligible (message, activity_type, recipient)

Dispatcher determines per-channel eligibility via Membership::Notifiable at message creation.

2
Find-or-create active bundle

User#active_notification_bundle returns the open bundle or creates one via private open_notification_bundle!. Window = 1h or 24h, snapshotted from email_frequency. Race-safe via partial unique index index_notification_bundles_active_per_user. BundleDeliveryJob scheduled with wait_until: ends_at on first item insert (bundle.previously_new_record?).

3
Insert NotificationBundleItem

(bundle_id, message_id, kind, actor_id). Unique index on (bundle_id, message_id, kind) dedups within a window.

⏱
Bundle window passes

1 hour or 24 hours, depending on frequency. New eligible items keep landing in the same bundle.

4
BundleDeliveryJob fires

Walks bundle.items, asks membership.receives_missed_email_for?(item.message, item.kind) for each.

⊘
All items dropped

User returned, blocked sender, opted out, message deleted, account flag flipped. Bundle marked canceled_at; no email.

✓
Items remain → deliver

MissedNotificationsMailer.bundle(user, items) sends with X-Idempotency-Key: bundle-#{bundle.id}. delivered_at set on success.

Send-time revalidation is the cancellation path

No active job cancellation, no per-item bookkeeping. State changes during the window — user reconnects, opts out, blocks sender, account flag flips — drop items at delivery. If all items drop, the bundle is canceled.

Idempotent retry via provider-side dedup

Every send sets the header X-Idempotency-Key: bundle-#{bundle.id}. Resend: the delivery method forwards this as the idempotency_key: param on Resend::Emails.send — 24-hour server-side dedup. SES: no per-call idempotency parameter on send_email, so the header is stripped before the raw mail is sent and the only retry safety net is the job's own retry_on / terminal-error rescue policy. Provider-side dedup (where it exists) fails open rather than failing closed like a "claim before deliver" pattern would.

Cooldown

Bundle window is the cooldown. There is no separate per-membership cooldown column. A second mention 30 seconds after the first lands in the same bundle and produces a single email at delivery time.

Bundle GC

Folded into the weekly digest job's per-workspace loop — no separate cron. Delivered or canceled bundles > 90 days old are delete_all'd. Active bundles never pruned (bounded to one per user via the partial unique index).

08 Weekly activity digest

Independent pipeline. Different copy, different cadence, different opt-out, different gates. Generated content per send — no persistent bundle.

1
Cron fires WeeklyDigestJob

Weekly per workspace. Two-job fan-out: WeeklyDigestRunnerJob (untenanted, iterates accounts) → WeeklyDigestJob (per-tenant via with_each_tenant).

?
account.weekly_digest_enabled?

If false, exit early. Admin-controlled per workspace, default off.

2
For each subscribed, healthy member

weekly_digest_subscribed, verified, active, not banned, not deactivated, not bot, no digest in last 6 days.

3
Generate content from accessible activity

(1) @everyone mentions in last week the user would have received a row for but didn't view. (2) Recently active rooms with N+ messages. (3) Small set of public excerpts. No DMs, no inaccessible rooms.

⊘
No qualifying content

Skip user. Do not send empty digest. last_digest_sent_at is not updated — re-evaluated next week.

✓
Content available → deliver

WeeklyDigestMailer.digest(user, content). Set last_digest_sent_at. Surface-scoped unsubscribe token (:weekly_digest) — independent of missed-notification opt-out.

Sends regardless of recipient activity. A subscribed member who was active every day this week still receives the digest. The on/off subscription is the only gate, plus 6-day dedup. A presence-aware "only-if-inactive" gate was rejected — it weakens the simple opt-in mental model and creates "I subscribed but didn't get one" confusion.

09 Multi-tenant boundaries

Identity and email address are the only untenanted touchpoints. Everything else is per-workspace.

Lives on Storage Effect
User::NotificationSettings Tenanted DB Per-workspace. A user in workspaces A and B has independent settings in each.
Notification::Bundle + Item Tenanted DB Bundles are per-workspace. Cross-workspace consolidation is out of scope.
Account email flags Tenanted DB Per-workspace admin toggles (email_notifications_enabled, weekly_digest_enabled).
Push::Subscription Tenanted DB Existing — already per-workspace.
last_digest_sent_at Tenanted DB Per-workspace dedup. A user gets one digest per workspace per week.
Email address Untenanted (GlobalIdentity in SaaS) One outbound address regardless of which workspace fired the email. Subject/From line carries the workspace name.

Unsubscribe tokens carry { user_id, tenant, surface }. The unsubscribe controller decodes the token, enters the encoded tenant via ApplicationRecord.with_tenant(...), then flips the appropriate column based on surface. A click from workspace A's missed-notification email does not affect workspace B or A's digest subscription. Self-hosted: tenant: nil, with_tenant is a no-op.

10 User & account defaults

Default-safe rollout. Email gated off at the account level until deliverability is proven; both email surfaces default off for users — except weekly digest, which defaults subscribed because the digest is admin-enabled with member opt-out (PRD § Product principles #6).

Existing & new users
missed_email_enabled false weekly_digest_subscribed true push_enabled true mode mentions_and_dms email_frequency hourly
Account (admin)
email_notifications_enabled false weekly_digest_enabled false

Two-layer reconciliation: global mode × per-room involvement

State Push Missed email Digest In-app row
mode: nothing (no per-room override) suppressed suppressed unaffected created
mode: nothing + involvement: everything fires (per-room override) fires unaffected created
missed_email_enabled: false unaffected suppressed unaffected created
weekly_digest_subscribed: false unaffected unaffected suppressed created
push_enabled: false suppressed unaffected unaffected created

In-app rows are created regardless of mode — the Activity tab is the truth-on-return surface.

11 Scope

v1 is bounded. Bounce handling, snooze, thread-reply email, and per-room email controls all defer.

In v1

  • Mention & DM bundled email
  • @everyone bundled email (only for recipients who'd get an in-app row)
  • Hourly / daily user-selectable bundle window
  • Send-time revalidation
  • Provider-side idempotency for retry safety
  • Weekly activity digest (admin-enabled, member opt-out)
  • RFC 8058 List-Unsubscribe headers
  • Surface-scoped unsubscribe (digest vs missed)
  • SaaS = SES, self-hosted = Resend
  • Two-layer reconciliation (global mode × per-room involvement)

Deferred to v1.1+

  • Thread-reply email (recipient set already wired; gated on v1 bundle-volume telemetry)
  • Per-room email controls
  • Reply-from-email
  • Cross-workspace bundle consolidation
  • Snooze / DND / pause notifications (not in any form)
  • Bounce / complaint / suppression handling (webhooks land in v1.1)
  • Personalized digest ranking (Discord Highlights-style)
  • Admin-authored digest content
  • Per-user timezone digest send time
  • Per-workspace BYO sending domain
